# Files, companies and recruiters

## Why

Three gaps, all of them things a job search actually needs:

- **The documents are missing.** The exact CV and motivational letter that went out with an
  application live in a folder somewhere, not in Jobify. The only file handling that exists is
  `POST /account/profile/resume`, which reads an uploaded resume for its text and saves nothing.
- **A company is a string.** `jobs.company` is text, so there is nowhere to put a company's
  website, what you know about them, or the three roles you have with them across two hunts.
- **A recruiter is two text fields.** `jobs.contactName` and `jobs.contactEmail` hold one person
  per job, with no way to see that the same agency recruiter pitched you four of them.

The job-application-tracker solves all three. This takes its shape — attachments on disk beside
the database, companies and contacts as first-class records — and fits it to Jobify's
server-based, multi-user, hunt-scoped model, so adding a job from a phone keeps working exactly
as it does now.

## Phase 1 — Files on a job

### What changes

The job detail page gets a **Files** card: drag or pick a file, give it a kind, and it is stored
on the server beside the database. Each file shows its kind, size and when it was added, and can
be downloaded, renamed or deleted.

```
Files (3)
  Resume_backend_2026.pdf   CV      1.2 MB   [use as this job's resume]
  motivation_acme.pdf       Cover   88 KB    [use as this job's cover letter]
  offer_acme.pdf            Offer   240 KB
```

A stored CV or cover letter can be pushed into the job's own text fields: **use as this job's
resume** runs the file through the existing `users/resume-text.ts` extractor (PDF via `unpdf`,
`.docx` via `mammoth`, otherwise UTF-8) and puts the text in `jobs.profile.resume`, so the AI
tasks and job chat tailor themselves to the CV that actually went out. The same for a cover
letter into `jobs.coverLetter`. The text is handed to the form for review, as the profile's
resume upload already does; nothing is saved behind the user's back.

### How it's stored

New `attachments` table, per user like everything else:

| column                          | notes                                                                                                                                  |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `userId`                        | not null, cascades. Every query filters by it.                                                                                         |
| `jobId`                         | nullable, cascades. `companyId` / `contactId` are added in phases 2 and 3; a row with all three null is a file in no particular place. |
| `kind`                          | `ATTACHMENT_KINDS`: `resume`, `cover_letter`, `posting`, `offer`, `other`.                                                             |
| `name`                          | the original file name, shown and renameable.                                                                                          |
| `path`                          | relative to `files/`, unique, always generated by the server.                                                                          |
| `contentType`, `size`, `sha256` | type guessed from the **name**, never from the browser's claim; hash indexed so identical files can be spotted later.                  |

Files live under `DATA_DIR/files/YYYY/MM/<id>-<safe-name>`, next to `jobify.db` and `logs/`, so
the existing `/data` volume covers them with no new mount. A new `files/attachment-store.ts` owns
the disk:

- `safeName()` — ASCII, no path separators, extension kept, length capped.
- `save()` — writes to `DATA_DIR/.tmp` first and renames into place, hashing as it goes.
- `resolve()` — refuses anything that is not under `files/`, and refuses symlinks.
- `remove()`.

Uploads use `FileInterceptor` with multer's default in-memory storage, as the resume route
already does, capped by `ATTACHMENT_FILE_MAX_BYTES` (25 MB, `FILE_MAX_BYTES` in the config
object). Multer stays a transitive dependency: nothing imports it directly.

### API

| route                    | notes                                                                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /jobs/:id/files`   | multipart `file` + `kind`.                                                                                                                                               |
| `GET /jobs/:id/files`    | the job's files, newest first.                                                                                                                                           |
| `GET /files/:id/content` | PDFs, images and plain text open inline; everything else downloads. `X-Content-Type-Options: nosniff` on both, so a file can never run as a page on Jobify's own origin. |
| `POST /files/:id/text`   | the file's text, for the "use as…" buttons.                                                                                                                              |
| `PATCH /files/:id`       | name, kind.                                                                                                                                                              |
| `DELETE /files/:id`      | row first, then the file.                                                                                                                                                |

### Files that outlive their row

Deleting a job removes its attachment rows by cascade, and deleting a hunt or a user does it two
levels down, so the service cannot always know which paths to unlink. `FilesService` deletes the
files on the single-job path explicitly, and a `deleteOrphans()` sweep — every path on disk with
no row behind it — runs on startup next to `HuntsService.adoptOrphanedJobs` and after a hunt or
user is deleted.

### Backups

Backup version 3, with a zip beside the JSON:

- `GET /backup/zip` → `backup.json` plus `files/…`, self-contained.
- `POST /backup/import/zip` → multipart, restores both.
- The JSON export and import keep working. Version 3 JSON records each file's kind, name, type,
  size and hash so the list survives, and a JSON-only import says plainly that the bytes were
  not in the file. Version 1 and 2 backups still import.

One new server dependency, `fflate`, which reads and writes zips in a few kilobytes of pure JS.

### Tests

`attachment-store.spec.ts` (safe names, path traversal, symlinks, the size cap), a
`files.service.spec.ts` against `createTestDatabase()` and a temp dir, and a zip backup
round-trip.

## Phase 2 — Companies

### What changes

A **Companies** page lists every company you have a job with, how many jobs and how many are
still open. A company has a page of its own: its jobs **across all hunts**, its website, what you
know about it, its people (phase 3) and its files. The job form's company box suggests companies
you already have and creates one on the spot for a name it does not know, like `TagPicker` does
for tags. The job detail page shows the company as a chip that opens that page.

### How it's stored

New `companies` table: `userId` (cascades), `name`, `website`, `isAgency`, `about`, timestamps,
unique on (`userId`, `name`) with `CompaniesService.forName` matching case-insensitively first —
the `lower(trim(…))` trick `findDuplicates` already uses — so "ACME" and "Acme" are one company.
Collapsing the tracker's separate `agencies` table into an `isAgency` flag saves a table and a
set of routes for no loss on screen.

`jobs.companyId` is added as a nullable FK, nullable only for rows that predate it, and
`CompaniesService.adoptOrphanedJobs()` fills it in on startup from `jobs.company` — the same
pattern as `huntId`. Note that drizzle-kit omits `ON DELETE` on columns added by `ALTER TABLE`,
so the generated migration needs it added by hand.

**`jobs.company` stays, as the company's name written through.** It is no longer edited directly:
whenever a job's `companyId` is set the name is copied with it, and renaming a company updates its
jobs' `company` in the same transaction. That one invariant, in two services, keeps the job list,
the stats, duplicate detection, the CSV and every existing backup working unchanged on a plain
text column, while the FK carries the company page, its contacts and its files. The alternative —
projecting `company` from a join everywhere — touches `JobsService`, `StatsService`,
`BackupService` and the duplicate finder for the same result on screen.

Importers and job search are untouched: drafts carry a company name as they do today, and the
insert path resolves it to a company.

### API

`GET /companies` (with counts), `POST /companies`, `GET /companies/:id` (the company, its jobs,
its files), `PATCH /companies/:id`, `DELETE /companies/:id` — refused with a 409 while it still
has jobs, so a company can never take a job's identity with it.

### Pages

Two new routes and a nav item (`Building2`), sitting below **Job hunts** since neither is
hunt-scoped — no `handle: { hunt: true }`, so no finished-hunt banner.

- **`/companies`** — a searchable grid of cards: name with an _Agency_ badge, website, how many
  jobs and how many are still open, when you last did something there, and (phase 3) chips for
  the people you know there. Search matches name and website; **All / With open jobs / Agencies**
  narrows it; sort by name, most jobs or recent activity.
- **`/companies/:id`** — the company's page: name, badge, website and **Edit** / **Delete** in
  the header, then cards for its **jobs grouped by hunt** (status badge, title, applied date,
  each linking to the job), its **people** (phase 3), its **files** (phase 1), and **About**
  rendered through the existing `Markdown` component.

Counts and the job list cover every hunt, which is the point of the page: three roles at one
company across two searches is exactly what `jobs.company` as text cannot show today.

## Phase 3 — Recruiters and contacts

### What changes

A **Recruiters** page lists everyone you deal with as tiles: agency recruiters, people at
companies, independents, with their job title, a chip for where they work, their email and phone,
and what you have in progress with them. Each person has a page: how to reach them, every job
they are part of and as what, your notes about them, their files.

A job's single contact pair becomes a list: **Recruiter**, **Hiring manager**, **Interviewer**,
**Referrer** or **Other**, each a person who exists in their own right.

### How it's stored

- `contacts`: `userId` (cascades), `companyId` (nullable — where they work; an agency recruiter
  works at a company with `isAgency` set), `name`, `title`, `email`, `phone`, `linkedinUrl`,
  `notes`, timestamps. The tracker's separate `contact_details` table, which exists for people
  with several emails, is collapsed into columns; a second address can wait until it is missed.
- `job_contacts`: `jobId` and `contactId` (both cascade) plus `relation` from
  `CONTACT_RELATIONS`, unique per (job, contact, relation).
- `attachments` gains nullable `companyId` and `contactId`, so a file can hang off a company or a
  person — the CV you sent a recruiter — as well as a job.
- `jobs.contactName` / `contactEmail` are migrated on startup into a contact and a `recruiter`
  link, then dropped from the form and the detail page. Version 2 backups that carry them still
  import, through the same path.

Companies and contacts are **per user, not per hunt**: a recruiter you know is still a recruiter
you know in next year's search, and their page shows jobs from every hunt.

### API

`/contacts` CRUD plus `GET /contacts/:id` (their jobs and company), and
`POST`/`DELETE /jobs/:id/contacts` for the links. Backup version 3 carries `companies` and
`contacts` lists and each job's contact links by index, the way hunts are already carried.

### Pages

Two more routes and a **Recruiters** nav item (`Contact`), beside Companies.

- **`/contacts`** — tiles, A to Z: name, job title, a chip for their company or agency that
  opens that company's page, every way to reach them as a working link (`mailto:`, `tel:`, the
  LinkedIn profile), and what you have in progress with them (_2 jobs in progress_). Search
  matches name, title, company, email and phone; **All / Agencies / Companies / Independent /
  In progress** narrows it, where _in progress_ means a job of theirs at a status in
  `ACTIVE_STATUSES` that is not archived.
- **`/contacts/:id`** — their page: how to reach them, every job they are part of **across all
  hunts** with a badge for the relation (recruiter, hiring manager, interviewer, referrer),
  their company, your notes and their files.

The job detail page gains a **People** card with the same chips, and the job form a contact
picker that suggests existing people and creates one inline, like the company box.

## Share to Jobify (independent of phases 1–3)

### Why

Jobify is already the right shape for this — the server fetches and parses the posting, so the
phone only has to hand over a link. What is missing is the handing over: today it means opening
Safari, finding the tab, navigating to **Add job** and pasting. The goal is seeing a role in the
LinkedIn app, hitting **Share**, and being done.

### What iOS actually allows

Safari does not implement the Web Share Target API, so an installed home-screen web app **cannot**
appear in the iOS share sheet. The WebKit request has been open since 2019 with no timeline, and
nothing has changed as of this writing. Any claim to the contrary should be checked against
caniuse and the WebKit release notes before being believed.

What does work is the **Shortcuts** app: a shortcut with _Show in Share Sheet_ enabled appears in
the share sheet of every app, takes the shared URL as its input, and can either open a URL or
make an HTTP request. So the share sheet entry is a shortcut named **Add to Jobify**, and the
work on Jobify's side is to give that shortcut something good to call.

### Installable first

No manifest exists today, so "installed" currently means a Safari bookmark with browser chrome.

- `apps/web/public/manifest.webmanifest`: name, `short_name` "Jobify", `start_url` and `scope`
  `/`, `display: standalone`, the theme color already in `index.html`, and 192/512 plus maskable
  icons generated from `favicon.svg`.
- `index.html`: the manifest link, a 180×180 `apple-touch-icon`, `apple-mobile-web-app-capable`,
  `apple-mobile-web-app-status-bar-style` and `apple-mobile-web-app-title`.
- A **minimal service worker** — a fetch handler that does nothing but pass through — registered
  from `main.tsx`. It exists so Chrome treats the app as installable and honours `share_target`;
  it caches nothing, so there is no stale-bundle failure mode. Offline use is out of scope: an
  app whose data lives on a server has little to do offline.
- `manifest.webmanifest` also declares a `share_target` (`method: "GET"`, params `url`, `text`,
  `title`) pointing at `/share`. Android and desktop Chrome then get a real share target for
  free; iOS ignores it, which is why the shortcut exists.

These are static files out of `apps/web/dist`, which `ServeStaticModule` already serves at the
root, so the service worker's scope is right with no server change.

### The landing route

`/share` is a thin route that forwards to **`/jobs/new?url=…`** (also `?text=` and `?title=`),
and `NewJobPage` learns to read those search params: with a URL it calls `POST /import` straight
away, shows a spinner, and drops you on the prefilled form with the duplicate check intact. With
shared text it takes the first URL it finds, and failing that posts the text itself, which the
server's `text-draft.ts` path already handles. If the import fails — a login wall, a dead link —
the form opens anyway with the URL filled in and the error shown, so the role is still one tap
from saved. This alone makes a share-sheet shortcut useful with no further server work.

For a shared LinkedIn posting this lands well already: `lnkd.in` short links resolve because
`HttpFetcher` follows redirects, and `LinkedInParser` reads the logged-out guest endpoint, so a
share from the LinkedIn app becomes a full draft with title, company, location and description.

### One tap vs none

Two shapes of shortcut, both documented in `docs/`:

1. **Review, then save** — _Open URL_ `https://<your-host>/jobs/new?url=[Shortcut Input]`. Works
   the moment the landing route ships, reuses the session cookie, and you see what was imported
   before it is saved.
2. **Saved without leaving the app** — _Get contents of URL_, `POST` to `/api/share` with
   `Authorization: Bearer <token>` and `{"url": "[Shortcut Input]"}`, then _Show notification_
   with the title that comes back. This is the version that makes capturing a role instant, and
   it needs two new server pieces:

- **Personal access tokens.** An `api_tokens` table following the `sessions` pattern exactly —
  `userId`, `name`, the SHA-256 hash of the token, `lastUsedAt` — with `AuthGuard` also accepting
  `Authorization: Bearer <token>`, and a Settings → Account section to create, copy once and
  revoke them. A token carries the same rights as a session, so `@AdminOnly()` still gates what
  it gated before.
- **`POST /share`.** Takes `{ url }` or `{ text }`, runs the importer and `enrichDraft`, and
  saves the job into the active hunt through `HuntsService.forNewJob` at status `saved`. It
  returns `{ id, title, company, duplicate }` so the notification can say _Saved_ or _Already
  saved_ — a duplicate answers 200 with the job it matched rather than the 409 the interactive
  path uses, because there is no dialog to show on a phone. `ThrottlerGuard`, as on the other
  unattended routes.

Because the host and token differ per install, the Settings page shows the exact URL and the
shortcut's actions to copy, rather than the docs guessing.

## Provenance and licensing

Jobify is AGPL-3.0-or-later; the job-application-tracker this borrows from is Apache-2.0
(`NOTICE`: Copyright 2026 Kai Waddington). Apache-2.0 is one-way compatible with (A)GPLv3, so
Apache-licensed code _may_ be included here — the reverse is not true — but that is not what is
happening: **nothing is copied.** The data model, the route shapes and the safety rules above
were written from reading how that project behaves, and the implementation is fresh TypeScript in
Jobify's idiom. Designs, schemas and API shapes are not copyrightable; a line-by-line translation
of a function would be a derivative work, so `storage/files.py` in particular is a reference for
_what to get right_ (names, traversal, symlinks, atomic writes), not a file to transliterate.

If any file does end up closely derived, it carries the Apache attribution and the NOTICE text
travels with it, per section 4(d). Either way the tracker is credited by name here and in any
pull request, so whoever merges it is not left guessing where the design came from.

New dependency: `fflate` (MIT), compatible with AGPL.

## Running a modified build

The container story is already solved by the repo's own CI, which builds
`ghcr.io/${{ github.repository }}` — **a fork publishes to its own namespace with no workflow
changes**, `:edge` on every push to the fork's `main`. So a modified server is a fork, a push, and
`image: ghcr.io/<you>/jobify:edge` in the compose file. Three things to know:

- A new fork has Actions **disabled** until they are enabled in its Actions tab, and its GHCR
  package is **private** by default — either make the package public or `docker login ghcr.io` on
  the server with a token that has `read:packages`.
- The `linux/arm64` half of the build goes through QEMU and is slow; drop it from `platforms` if
  the server is amd64.
- Migrations are forward-only, so copy the `/data` folder (or export a backup) before running a
  modified image against real data for the first time. Going back to an upstream image after new
  columns exist is not supported.

Each phase above is a self-contained topic branch off `upstream/main` — the phases were scoped
that way on purpose — with a separate branch that merges them for deployment, so what runs on the
server never becomes what a pull request has to be untangled from. Jobify's CONTRIBUTING asks for
an issue before larger changes, which all of these are.

## Left out on purpose

- **The document library.** The tracker's `documents` / `document_versions` /
  `application_documents` — a CV called "Backend CV" with versions, and which version went with
  which application — and the "which CV gets replies" insight built on it. Attachments carry a
  hash, so the same file in several places can be recognised later and folded into versions
  without a data migration.
- **The recruiter CRM.** Calls and meetings with an agenda and notes, waiting-on-them and
  reply-to-read state, reply-time stats, per-recruiter scorecards, duplicate merging, favourites.
  This is the largest part of the tracker and the natural phase 4; the tables above are shaped so
  it bolts on rather than replacing anything.
- **Files in the AI prompts.** A file's text reaches the AI only when the user puts it in a
  resume or cover-letter field. Nothing reads attachments on its own.
- **Image thumbnails, previews and OCR.** Files are stored and served, not processed.
- **Per-company and per-recruiter stats** on the dashboard, and filtering the job list by
  company or recruiter. Both are cheap to add once the tables exist.
- **Offline use and a caching service worker.** The worker added for installability passes every
  request through. Caching the app shell is a separate decision with its own failure modes.
- **A native iOS app** (or a wrapper) purely to get a real share extension, and push
  notifications. The shortcut gets to the same place for a fraction of the work.
- **Sharing a file or a screenshot into Jobify.** `share_target` can accept files on Android, and
  the shortcut could upload one to a job, but it needs a job to attach to, so it waits until
  phase 1 is in use.
